# ContentIQ AI

A multimodal AI content intelligence platform that turns documents, videos, and YouTube links into searchable, grounded, and verifiable knowledge — real extraction, real embeddings, real vector search, real LLM generation, and real AI-output grounding checks throughout, with nothing faked.

Built around problem statement **SIH26154**.

## What it actually does

- Upload a **PDF, DOCX, or TXT** file, paste raw **text**, upload a **video/audio** file, or paste a **YouTube URL**.
- The platform extracts real content (`pdfjs-dist` for PDFs with per-page text, `mammoth` for DOCX, Gemini's multimodal Files API for uploaded video/audio transcription, `youtube-transcript` + oEmbed for YouTube), chunks it, embeds every chunk with Gemini's embedding model, and stores the vectors in **MongoDB Atlas Vector Search**.
- Ask questions about your content — answers are retrieved via real vector similarity search and generated by Gemini, grounded strictly in the retrieved excerpts, with real page/section/timestamp citations. If nothing relevant is found, it says so instead of guessing.
- Generate summaries, key points, FAQs, MCQs, a slide deck, and more — all derived from the actual extracted content, not templated strings.
- Run **AI output grounding/consistency verification**: claims are extracted from generated output and checked against the source's own retrieved chunks, flagging contradictions, softened numbers, or unsupported statements. This is a grounding check, not a guarantee of perfect factual correctness.
- Everything is persisted per-user in MongoDB — projects, sources, chunks, outputs, verification reports, and Q&A conversation history all survive logout/login.

## Architecture

```
PDF / DOCX / TXT / Video / Audio / YouTube / Pasted Text
                    │
                    ▼
   Real extraction (pdfjs-dist / mammoth / Gemini Files API / youtube-transcript)
                    │
                    ▼
        Paragraph/sentence-aware chunking (page / section / time-range preserved)
                    │
                    ▼
          Gemini embeddings → MongoDB Atlas Vector Search
                    │
        ┌───────────┼────────────────────┐
        ▼           ▼                    ▼
   RAG Q&A    Summaries/MCQs/PPT   Grounding Verification
  (cited)     (Gemini, grounded)   (claim extraction + judge)
        │           │                    │
        └───────────┴────────────────────┘
                    │
                    ▼
              React frontend
```

Background processing (extraction + generation) runs as an **Agenda** (MongoDB-backed) job in a separate worker process — the API only enqueues jobs, so a `POST /api/sources/upload` or `/api/transformations/generate` returns immediately with a `jobId`, and the frontend polls `GET /api/jobs/:id` for real `QUEUED → PROCESSING → COMPLETED/FAILED` progress.

### Why MongoDB Atlas + Gemini, not Postgres/pgvector + "any LLM"

The original spec described Postgres+pgvector and a swappable LLM provider. Per the user's explicit choice for this build: **MongoDB Atlas** (native Atlas Vector Search) replaces Postgres+pgvector, and **Google Gemini** is the fixed LLM/embedding provider (`@google/genai`). The `LLMService`/`EmbeddingService` abstraction still isolates all model calls behind one interface, so swapping providers later only touches those two files.

### Why Agenda instead of Redis+BullMQ

No Redis was available in the dev environment. Agenda provides the same QUEUED/PROCESSING/COMPLETED/FAILED job lifecycle backed by MongoDB (already required for the app), avoiding a second infra dependency. It's a known trade-off — Agenda's ecosystem is smaller/staler than BullMQ's — so job access is isolated behind `services/jobService.ts` for easy replacement.

### Why Gemini Files API instead of FFmpeg + Whisper

No ffmpeg/Whisper were available locally. Uploaded video/audio is instead sent directly to Gemini's multimodal Files API, which is asked to return a structured, timestamped transcript. This is genuinely real transcription (not fabricated), but timestamps are the model's own estimate from watching/listening, not frame-accurate ASR — this is called out directly in the UI/Verification copy.

## Setup

### 1. Prerequisites

- Node.js 20+
- A **MongoDB Atlas** cluster (the free M0 tier supports Atlas Vector Search) — get a connection string from the Atlas UI.
- A **Gemini API key** from [Google AI Studio](https://aistudio.google.com/apikey).

### 2. Configure environment variables

```bash
cp server/.env.example server/.env
# then edit server/.env: set MONGODB_URI, JWT_SECRET, GEMINI_API_KEY

cp .env.example .env
# VITE_API_URL defaults to http://localhost:5000/api, adjust if needed
```

`EMBEDDING_MODEL`/`EMBEDDING_DIMENSIONS` must be decided **before** creating the vector index — the dimension count is baked into the index at creation.

### 3. Install dependencies

```bash
npm install
cd server && npm install
```

### 4. Create the Atlas Vector Search index (one-time)

```bash
cd server
npm run db:setup-index
```

This creates a `vector_index` on the `contentchunks` collection and polls until it's queryable.

### 5. Run locally

```bash
# Terminal 1 — API server
cd server && npm run dev

# Terminal 2 — background worker (required for uploads/processing to complete)
cd server && npm run worker

# Terminal 3 — frontend
npm run dev
```

Visit the frontend, register an account, and create your first transformation.

### 6. Run with Docker Compose

```bash
docker compose up --build
```

MongoDB stays Atlas-hosted (not containerized) — the compose file only runs `frontend`, `backend`, and `worker`, all pointed at `server/.env`.

## Environment variables (`server/.env`)

| Variable | Purpose |
|---|---|
| `MONGODB_URI` | MongoDB Atlas connection string |
| `JWT_SECRET` | Secret for signing auth tokens |
| `GEMINI_API_KEY` | Google Gemini API key |
| `GEMINI_MODEL` | Generation model (default `gemini-3.5-flash-lite`) |
| `GEMINI_GENERATION_RPM` | Proactive cap on generateContent calls/minute (default `4`, safe for the free tier's 5 RPM limit — raise on a paid tier) |
| `EMBEDDING_MODEL` | Embedding model (default `gemini-embedding-001`) |
| `EMBEDDING_DIMENSIONS` | Must match the Atlas index (default `768`) |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | Chunking tuning (characters) |
| `TOP_K` / `SIMILARITY_THRESHOLD` | Retrieval tuning |
| `UPLOAD_DIR` / `MAX_UPLOAD_MB` | File upload storage/limits |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` | Rate limiting on AI-backed routes |

See `server/.env.example` for the full list with defaults.

## Testing

```bash
# 1. Start the server (+ worker) with real credentials configured
cd server && npm run dev &
cd server && npm run worker &

# 2. Run the integration suite
cd tests
pip install -r requirements.txt   # pytest, requests
pytest
```

The suite exercises real content end-to-end: registration/login, cross-user authorization (403s), real PDF/DOCX/text ingestion via `rawText`, grounded RAG Q&A (including an out-of-scope refusal and an adversarial contradiction check), MCQ generation, verification, and the async job lifecycle. Assertions are structural (shape, ranges, presence) rather than pinned to exact wording, since a real LLM's phrasing varies run to run.

## Known limitations

- **PDF/DOCX are text-only** — embedded images, charts, and diagrams are not multimodally analyzed.
- **DOCX has no real page numbers** (DOCX doesn't store pagination) — its citations use section/heading references instead of page numbers.
- **Uploaded video/audio timestamps** come from Gemini watching/listening to the file, not frame-accurate speech recognition — treat them as close estimates.
- **YouTube transcript fetching** uses an unofficial, key-free scraper of YouTube's caption endpoints; it can break if YouTube changes its internals, and surfaces as a real error rather than a fabricated fallback.
- **Agenda** (MongoDB-backed jobs) is used in place of Redis+BullMQ; it's a reasonable trade-off for this environment but has a smaller ecosystem — swap it via `services/jobService.ts` if Redis becomes available.
- **Verification is a grounding/consistency check**, not exhaustive fact-checking — it compares generated claims against the same source's retrieved chunks via an LLM judge, which can itself make mistakes.
- **Analytics** exposes a public `/api/analytics/telemetry` (aggregate, no per-user content) alongside an authenticated `/api/analytics/summary` (your own stats).
- **Gemini's free tier is rate-limited** — as low as 5 requests/minute *and* a hard ~20 requests/day cap per model, confirmed live during testing against `gemini-2.5-flash` (also flagged by Google's own API as being sunset for new users — the default model was switched to `gemini-3.5-flash-lite`, which had separate, unexhausted quota). `GEMINI_GENERATION_RPM` (default 4) proactively paces every generation call through a sliding-window limiter so a single transformation's parallel calls (summary, PPT, MCQs, document intelligence) queue instead of bursting into a 429, and parses Gemini's own suggested `retryDelay` on a 429 rather than guessing. Every Gemini call also has a hard 90s client-side timeout with retry — live testing surfaced a call that hung indefinitely with no response and no error, which a bare SDK call would never have recovered from. On the free tier, a transformation with several output types will visibly take longer because of this pacing, and heavy same-day testing can exhaust the daily cap outright — for real multi-user production traffic, move to a paid Gemini tier and raise `GEMINI_GENERATION_RPM` accordingly.
- **PDF parsing uses `pdfjs-dist` directly**, not the popular `pdf-parse` wrapper — `pdf-parse` bundles a long-abandoned pdf.js from 2018 (v1.10.100) that was confirmed live during testing to reject a real, validly-generated PDF with a "bad XRef entry" error; `pdfjs-dist` (the current, actively-maintained parser) handled the same file without issue.
